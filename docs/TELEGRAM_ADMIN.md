# Telegram: управление заказами

Mini App команды: `/telegram/admin`. Отдельный бот, серверный API `/api/telegram/admin`, сессия только для работы с заказами. Будущий клиентский Mini App должен иметь отдельные маршруты и права; клиентская регистрация и текущий Telegram-бот не меняются.

## Подключение на Railway

1. Создайте отдельного бота через [BotFather](https://t.me/BotFather), `/newbot`. Не используйте токен клиентского бота.
2. Добавьте переменные в серверный сервис Railway, без префикса `VITE_`:
   - `TELEGRAM_ADMIN_BOT_TOKEN`: токен нового бота.
   - `TELEGRAM_ADMIN_USER_IDS`: числовые Telegram user ID сотрудников через запятую. Не username, не ID группы. Проверяйте принадлежность каждого ID сотруднику.
   - `TELEGRAM_ADMIN_APP_URL`: `https://evergreenmarket.com.ua/telegram/admin`.
3. В BotFather настройте Menu Button (`/setmenubutton`) этого бота: название «Замовлення», URL из предыдущего пункта. При желании задайте тот же URL как Main Mini App.
4. Каждый сотрудник открывает личный чат с ботом и нажимает Start. Бот не отвечает на текстовые команды: доступ открывается кнопкой меню. Для этой версии webhook и polling административного бота не нужны. Не изменяйте webhook клиентского бота.
5. Перезапустите сервер после изменения переменных. Откройте приложение кнопкой меню: разрешённый аккаунт видит заказы, посторонний получает отказ. Удаление ID из списка и перезапуск отзывают даже уже выданную сессию.

Токен не помещать в Git, URL, клиентский код или чат. Существующие `TELEGRAM_BOT_TOKEN` и `TELEGRAM_CHAT_ID` относятся к прежнему клиентскому/операционному механизму, не заменять их. Без новых переменных Mini App закрыт; сайт продолжает работать. Миграция БД для этой функции не нужна.

Числовой ID можно получить из Telegram data export либо через одноразовый серверный запрос `getUpdates` к **новому** боту после `/start`. Не публикуйте ответ: он содержит личные данные. Новый бот не использует webhook, а клиентского бота для этого не опрашивать.

## Поведение

- Активные заказы и история, поиск по номеру/имени/контакту, фильтры статусов, страницы по 50 записей. Обновление раз в минуту, при возвращении в Telegram и вручную; на время подтверждения действия автообновление приостановлено.
- Карточка: контакты, комментарий, исторические цены/количества, текущее наличие и поставщик, безопасные ссылки, история действий. Скрытые/удалённые товары не теряют исторические строки заказа.
- Подтверждение → подготовка → готовность → выдача; отмена с причиной. В истории сохраняется Telegram ID сотрудника. При готовности используется существующий механизм уведомления покупателя.
- Новый заказ сохраняется до отправки уведомлений. Административный бот отправляет краткое сообщение каждому разрешённому ID и кнопку именно этого заказа. Сетевой отказ не блокирует оформление. Отправка best effort, без очереди повторов: при сбое ориентируйтесь на список заказов в панели.
- Сессия живёт 30 минут, только в памяти вкладки. После истечения нужно закрыть и открыть Mini App. Сервер проверяет Telegram-подпись и возраст initData до 5 минут, затем проверяет разрешённый ID на каждом запросе. Сессия Telegram не подходит к `/api/admin` и клиентским маршрутам.
- Проверка ожидаемого статуса предотвращает повторные и устаревшие действия. PostgreSQL блокирует строку заказа в транзакции для всех административных каналов до изменения остатков/счётчиков. Уведомление о готовности отправляется после сохранения.
- Веб-админка остаётся отдельным входом. Mini App не предоставляет редактирование каталога, массовые операции или закупку у поставщика.

## Проверки

`npm run test:telegram-admin`, `npm run test:storefront`, `npm run build`.

Безопасная демоверсия: `npm run preview:design`, затем `/preview/telegram-admin`. Данные вымышлены, изменения только в памяти вкладки, API записи блокируется preview-сервером. Демо не включается в production-сборку.

Перед использованием командой проверить на реальных Telegram iOS/Android: вход разрешённого/постороннего аккаунта, кнопку меню, клавиатуру, возврат, уведомление с открытием конкретного заказа, истечение сессии и отзыв доступа. Browser preview не заменяет эту проверку. Не создавать реальные покупательские заказы только для проверки дизайна.

Список первоначально читается через существующий репозиторий заказов и фильтруется на сервере. При росте истории стоит перенести фильтры/пагинацию в SQL. Гарантии одновременной работы нескольких серверов относятся к PostgreSQL; локальный JSON — только для одного процесса.

Официальная документация: [Mini Apps и проверка initData](https://core.telegram.org/bots/webapps#validating-data-received-via-the-mini-app), [кнопки бота](https://core.telegram.org/bots/api#inlinekeyboardbutton).
