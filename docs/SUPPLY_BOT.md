# Evergreen Supply: закупівлі кав’ярні

Внутрішній Telegram Mini App `/telegram/supply`, окремий від магазину й адмінки замовлень. Обидва партнери користуються одним робочим Telegram-акаунтом: один простір, спільні статуси, історія дій без призначення відповідального.

## Робочий цикл

1. «Сьогодні» показує неперевірені позиції, закупки та очікувані поставки.
2. «Перевірки»: склад і вітрина; щоденні або вибрані дні тижня. «Вистачає» означає запас до наступного можливого отримання. Неперевірена позиція не стає зеленою автоматично. Кількість — скільки замовити, не складський залишок.
3. «Замовити» / «Критично» формують одну відкриту закупку на постачальника. Можна скопіювати список і відкрити його Telegram/сайт.
4. «Замовили» натискають **після реального оформлення**. Потрібна дата отримання. Ці позиції не породжують повторне замовлення, доки поставка очікується.
5. «Отримали» підтверджує весь список і вимагає нової перевірки запасів. Часткову поставку поки залишають очікуваною, уточнюють дату і примітку; обліку часткових кількостей немає.
6. «Не замовляємо» потребує причини та дати перегляду (завтра — 30 днів). Невирішена потреба повертається в цей день; нова перевірка з дефіцитом може повернути її раніше.

Пропущений дедлайн не закриває закупку. Прострочені поставки видно в закупках і загальному нагадуванні. Два пристрої не перезаписують один одного: зміна перевіряє ревізію під PostgreSQL row lock; при конфлікті показується оновлений список і потрібен повтор дії. Видимий екран оновлюється кожні 30 секунд і при поверненні; відкриті форми не перезаписуються фоновим оновленням.

## Графіки й початкові дані

Постачальники та позиції редагуються через «Налаштування». Підтримано дедлайн кожного дня, дні доставки, мінімальний/максимальний термін у календарних днях, винятки на конкретні дати та відключення. Розрахунки — `Europe/Kyiv`, з переходом на літній час. Рекомендована дата враховує **максимальний** термін та наступний доступний день доставки; це планування, остаточну дату підтверджує постачальник.

Початковий список додається лише кнопкою в порожньому просторі. Milk Diller, Maya Cake, Panini Grill, OMOM — **непідтверджені чернетки** за наданим ТЗ. Дедлайни Panini та OMOM невідомі й залишені порожніми. Дні, терміни, одиниці та прив’язку товарів (особливо кави й витратних матеріалів) потрібно перевірити. Зміна графіка знімає його підтвердження; без підтвердження немає розрахованих обіцянок чи нагадувань про дедлайн.

## Підключення на Railway

Окремий бот для закупівель рекомендований, щоб його чат відрізнявся від клієнтських замовлень. Створіть бота через офіційного [BotFather](https://t.me/BotFather), збережіть токен **у змінних Railway**, не в GitHub або листуванні. У приватному чаті з ботом натисніть Start із спільного робочого акаунта.

На сервісі вебзастосунку задайте:

| Змінна | Значення |
|---|---|
| `TELEGRAM_SUPPLY_BOT_TOKEN` | Токен окремого бота |
| `TELEGRAM_SUPPLY_USER_IDS` | Числовий Telegram user ID спільного робочого акаунта |
| `TELEGRAM_SUPPLY_CHAT_ID` | Той самий ID приватного чату; має входити до дозволених ID |
| `TELEGRAM_SUPPLY_APP_URL` | `https://evergreenmarket.com.ua/telegram/supply` |
| `SUPPLY_REMINDERS_ENABLED` | `true` для хвилинної перевірки на постійно працюючому вебсервісі |

Також використовуються наявні `DATABASE_URL`, `JWT_SECRET` і `USE_POSTGRES=true`. Без окремого токена дозволено явно ввімкнути `TELEGRAM_SUPPLY_USE_SHARED_BOT=true`: тоді використовується наявний `TELEGRAM_BOT_TOKEN`. Це не надає доступу клієнтам; allowlist закупівель окремий. Ідентифікатор чату сам по собі не дозволяє вхід. Для спільного бота сценарій підключення зберігає його існуюче меню.

ID робочого акаунта можна взяти з його вже перевіреної конфігурації Telegram. Для нового окремого бота його також видно як `message.from.id` у відповіді Bot API `getUpdates` після Start. Не запускайте `getUpdates` для спільного бота, який уже обробляє оновлення іншим процесом. Не вставляйте токен у браузерний URL/історію чи командний рядок.

Публікація застосовує додаткову міграцію `20260920110000_supply_workspace` через звичайний `npm run railway:start` (`prisma migrate deploy`). Міграція створює тільки три нові таблиці: `supply_workspace`, `supply_notifications`, `supply_worker_status`; дані магазину не змінює.

Після розгортання й Start виконайте **в оточенні з цими змінними** `npm run supply:connect`. Команда перевірить бота, встановить кнопку «Закупівлі» для цього приватного чату окремого бота та надішле стартове повідомлення. Відкрийте Mini App кнопкою, уточніть початкові дані та увімкніть нагадування в його налаштуваннях. Прямий вхід із браузера закритий.

Для окремого планувальника існує `npm run supply:tick`. Запускайте з тими самими змінними й БД щохвилини, а `SUPPLY_REMINDERS_ENABLED` на вебсервісі залиште вимкненим. Якщо платформа присипляє вебсервіс, його вбудований worker не прокинеться сам: потрібен постійно працюючий сервіс або зовнішній планувальник. Milk Diller availability cron не змінено.

## Нагадування й надійність

- Загальні часи за замовчуванням — 11:00 і 17:00; змінюються в Mini App. Повторне нагадування стосується незавершених перевірок, закупок або затриманих поставок.
- На постачальника: 180/60/20 хвилин до дедлайну, змінюються в його картці. Нагадування є за наявності закупки **або неперевірених сьогоднішніх позицій**; повідомлення веде в потрібний розділ Mini App.
- Ключ події включає чат, постачальника, дату та етап. PostgreSQL зберігає спроби, відкладений повтор і факт відправлення; advisory lock координує серверні процеси. Перед надсиланням стан перевіряється повторно.
- Після простою надсилається лише поточний актуальний етап, без черги застарілих нагадувань. Після дедлайну повідомлення показує наступне вікно; потреба лишається відкритою.
- Telegram 429 враховує `retry_after`; тимчасові помилки повторюються. Збій після прийняття повідомлення Telegram, але до запису підтвердження в БД, може призвести до повтору. Це не гарантія exactly-once.
- «Зв’язок із Telegram» показує конфігурацію, свіжість worker, останнє повідомлення та помилку. Статуси змінюються в БД незалежно від доступності Telegram.
- Історія і завершені задачі зберігаються 90 днів (історія максимум 3000 подій; екран показує останні 100). Поточні незакриті задачі та останнє спостереження кожної активної позиції зберігаються довше, щоб очищення історії не зняло дефіцит.

Вхід перевіряє підпис і давність Telegram `initData` на сервері; JWT має окрему роль/audience закупівель, живе 8 годин, зберігається тільки в пам’яті сторінки. Доступ до замовлень клієнтів цей токен не дає. Робочий акаунт перевіряється за allowlist при кожному запиті. Нові дані не потрапляють у публічні API або каталог.

Офіційні контракти: [перевірка initData](https://core.telegram.org/bots/webapps#validating-data-received-via-the-mini-app), [кнопка web_app у приватному чаті](https://core.telegram.org/bots/api#inlinekeyboardbutton), [меню бота](https://core.telegram.org/bots/api#setchatmenubutton).

## Розробка та перевірки

- `npm run test:supply`: календар, дефіцит, повторні перевірки, конкурентні зміни API, авторизація, дедуплікація/повтор worker із тестовим сховищем.
- `npm run test:telegram-admin`, `npm run test:storefront`, `npm run build` — регресії інтеграції.
- `prisma validate` — перевірка схеми без виконання міграцій.
- `npm run preview:design` → `/preview/supply`: демонстраційний простір у пам’яті Vite, без БД і Telegram. Зміни демо йдуть тільки в `/__supply_demo`; `/api/*` зберігає read-only захист. Перезавантаження сторінки створює новий демопростір. Цей модуль не включається у production bundle.

Реальна приймальна перевірка після налаштування: Start → кнопка → вхід робочим акаунтом на двох пристроях → перевірка однієї позиції → спільна закупка → оформлення → отримання → повторна перевірка; потім одне контрольне нагадування. Локальні перевірки не підтверджують фактичну доставку Telegram чи роботу блокувань реального PostgreSQL.
